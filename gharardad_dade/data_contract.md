### پروژه: سیستم پرسش و پاسخ آفلاین مبتنی بر RAG روی اسناد PDF فارسی
### مسئول ماژول: فاطمه — ماژول F-01 تا F-08

> **این سند مکمل `schemas.py` است، نه جایگزین آن.** ساختار رسمی و الزام‌آور
> همان کلاس‌های `DocumentChunk` و `QAPair` در `schemas.py` هستند که باید در
> ریپازیتوری مشترک قرار بگیرند و توسط هر سه عضو import شوند. این سند فقط
> برای توضیح و استدلال پشت هر فیلد است.

## ۱. هدف این سند

این سند «قرارداد داده‌ای» بین ماژول من (Data Ingestion) و بقیه‌ی اعضای تیم است:

- **زینب** (موتور بازیابی معنایی — embedding و FAISS) → ورودی‌اش را از بخش «۲. خروجی چانک‌بندی» این سند می‌گیرد.
- **مشکات** (ماژول تولید پاسخ — LLM و prompt) → غیرمستقیم، از طریق چانک‌های بازیابی‌شده توسط زینب با این ساختار کار می‌کند.
- **ارزیابی نهایی تیم** → از بخش «۳. دیتاست ارزیابی» استفاده می‌کند.

هر تغییری در این ساختارها باید با اطلاع کل تیم انجام شود، چون تغییر بی‌هماهنگی باعث می‌شود کد بقیه از کار بیفتد.

## ۲. سه سطح داده‌ای که تولید می‌کنم

### سطح ۱ — خروجی استخراج متن (نتیجه‌ی F-02)

هر PDF بعد از استخراج، به این شکل نمایش داده می‌شود. نکته‌ی مهم: متن **به تفکیک صفحه** نگه داشته می‌شود، نه یکجا — چون بدون این کار، امکان استناد به شماره صفحه (که در بخش ۱۱ پروپوزال الزامی شده) از بین می‌رود.

```json
{
  "doc_id": "doc_0001",
  "filename": "sample.pdf",
  "source_type": "synthetic",
  "pages": [
    { "page_number": 1, "raw_text": "متن خام همان صفحه..." },
    { "page_number": 2, "raw_text": "متن خام همان صفحه..." }
  ]
}
```

| فیلد | توضیح |
|---|---|
| `doc_id` | شناسه یکتای سند، برای رهگیری در کل پایپ‌لاین |
| `source_type` | `"synthetic"` برای داده‌ی مصنوعی (فاز فعلی) یا `"real"` بعد از اتصال F-02 واقعی |
| `raw_text` | متن **قبل از** نرمال‌سازی — پاکسازی در سطح بعدی انجام می‌شود |

### سطح ۲ — خروجی چانک‌بندی (نتیجه‌ی F-03 + F-04) — تحویلی اصلی به زینب

خروجی این سطح یک **لیست تخت (flat list)** از چانک‌هاست، نه گروه‌بندی‌شده بر اساس سند —
چون ایندکس FAISS یکپارچه است و پیمایش مستقیم روی یک جریان تخت برای ماژول بازیابی ساده‌تر است.
هر چانک فیلد `doc_id` خودش را دارد تا اطلاعات تعلق به سند از دست نرود.

```json
[
  {
    "chunk_id": "doc_0001_c003",
    "doc_id": "doc_0001",
    "chunk_index": 3,
    "text": "متن نرمال‌شده و پاکسازی‌شده...",
    "page_number": 3,
    "char_start": 120,
    "char_end": 540,
    "token_count": 210
  }
]
```

| فیلد | توضیح |
|---|---|
| `chunk_id` | ترکیب `doc_id` + شماره ترتیبی، یکتا در کل سیستم |
| `doc_id` | سند مبدأ این چانک (چون دیگر گروه‌بندی تودرتو نداریم) |
| `chunk_index` | ترتیب چانک داخل همان سند (برای بازسازی توالی در صورت نیاز) |
| `page_number` | شماره صفحه‌ای که چانک از آن استخراج شده — **الزامی برای citation** |
| `char_start` / `char_end` | محل دقیق چانک در متن اصلی صفحه — برای دیباگ و ارزیابی همپوشانی (overlap) |
| `token_count` | تعداد تقریبی توکن — زینب برای مدیریت context length مدل embedding به آن نیاز دارد |

> نکته: اگر چانکی از دو صفحه عبور کند (متن پاراگراف بین دو صفحه شکسته شود)، `page_number` را برابر صفحه‌ای می‌گذاریم که **بیشترِ متن چانک** از آن آمده. این تصمیم را باید مستند نگه داریم چون روی دقت citation اثر مستقیم دارد.

### چرا فیلدهای `vector` و `score` در این سطح نیستند

این دو فیلد عمداً از خروجی من حذف شده‌اند، چون هر دو **derived data** هستند — یعنی داده‌ای که از روی خروجی من محاسبه می‌شود، نه بخشی از فرآیند آماده‌سازی سند:

- **`vector`**: تبدیل متن به بردار عددی وظیفه‌ی ماژول embedding (زینب) است، چون به مدل انتخابی (`intfloat/multilingual-e5-base`) وابسته است. اگر این مدل بعداً عوض شود، نباید نیازی به تغییر ماژول Data Ingestion باشد.
- **`score`**: میزان تطابق یک چانک با یک *سوال خاص* است — مقداری که فقط در لحظه‌ی اجرای واقعی retrieval (وقتی کاربر سوال می‌پرسد) معنا دارد، نه یک ویژگی ثابت و ذخیره‌شدنی چانک. این فیلد باید در یک ساختار جدا و در زمان اجرا (runtime output) تولید شود، مثلاً:
  ```json
  {"query": "...", "results": [{"chunk_id": "doc_0001_c003", "score": 0.87}]}
  ```

این دو مورد باید در قرارداد داده‌ای جداگانه‌ای تعریف شوند که مالکشان ماژول embedding/retrieval (زینب) است، نه ماژول Data Ingestion.

### سطح ۳ — دیتاست ارزیابی (نتیجه‌ی F-05 و F-06)

```json
{
  "doc_id": "doc_0001",
  "qa_pairs": [
    {
      "qa_id": "doc_0001_qa001",
      "question": "نویسنده در بخش دوم چه استدلالی مطرح کرده است؟",
      "question_type": "تفسیری",
      "answer_reference": "پاسخ مرجع انسانی...",
      "supporting_chunk_ids": ["doc_0001_c003", "doc_0001_c004"]
    }
  ]
}
```

`question_type` فقط یکی از سه مقدار زیر است (طبق تعریف بخش ۷ پروپوزال):
- `"مستقیم"` — پاسخ عیناً در یک چانک وجود دارد
- `"تفسیری"` — نیاز به استنتاج از یک یا چند چانک دارد
- `"مقایسه‌ای"` — نیاز به مقایسه بین چند سند/بخش دارد

## ۳. چرا الان «داده‌ی مصنوعی» و نه داده‌ی واقعی؟

چون F-02 تا F-04 (استخراج واقعی PDF) هنوز کامل نشده، ولی زینب و مشکات نباید بی‌کار بمانند. اسکریپت پیوست (`generate_synthetic_data.py`) دقیقاً همین ساختار را با داده‌ی جعلی ولی **کاملاً هم‌ساختار با خروجی نهایی واقعی** تولید می‌کند و تحویلی اصلی‌اش `mock_chunks.json` است. وقتی نسخه‌ی واقعی من آماده شد، فقط منبع داده عوض می‌شود — ساختار (schema) دقیقاً همین می‌ماند، پس کد زینب و مشکات نیازی به تغییر ندارد.

این الگو در مهندسی نرم‌افزار به آن **"mocking"** یا **"stub data"** می‌گویند — تولید داده‌ی جعلی هم‌شکل با داده‌ی واقعی، برای اینکه توسعه‌ی موازی ممکن شود. این دقیقاً همان الگویی است که زینب هم برای `MockLLMEngine` استفاده می‌کند.

## ۴. تفاوت مهم بین F-05 و F-06

- **F-05 (این فایل‌ها):** فقط برای تست *ساختار* داده است. سوال‌ها و پاسخ‌ها placeholder هستند و اهمیتی ندارد که محتوایشان درست باشد — فقط باید فرمت JSON درست و کامل باشد تا زینب بتواند کدش را رویش تست کند. خروجی این مرحله در `qa_pairs_draft.json` صرفاً یک نمونه‌ی ساختاری است.
- **F-06 (جدا و بعداً):** دیتاست واقعی و نهایی — ۵۰ جفت سوال-جواب دستی از اسناد واقعی، با پاسخ مرجع درست‌نوشته‌شده توسط انسان. این کار را نباید با این اسکریپت انجام داد.
